What is real-time?

The web was built for asking. Real-time needs telling.

Traditional web · request / response
Clientasks
GET /orders
Serveranswers

The client always initiates. The server can only respond to a question it was asked — it has no way to start a conversation.

After the response, the client holds a snapshot. It starts going stale the moment it arrives, and nothing tells the page.

Still the right model for 90% of what we build: pages, forms, search, CRUD.

Real-time web · event-driven
  1. Something happens. A row changes, a payment clears, another user types.
  2. The system detects it. Your API, the database's change log, or a third-party service like Stripe.
  3. The client gets notified. A pushed message — or it finds out on its next ask.
  4. The UI updates. Patch the cache, re-render, maybe animate the change.

The initiator flips: the world starts the conversation, not the user.

Every technique in this talk is a different answer to one question: after step 2, who tells the browser — and how fast?
⏱ 3:45 — 30 seconds. Left is not "legacy". It is the web, and it's fine. Right: stress step 2 — "the system detects it". That system might be our API, Postgres, or Stripe. Frontend engineers usually only see step 3 and 4, which is why we end up solving the wrong problem. Transition: so what is "real-time", really?

HTTPThe baseline

The browser only knows what it asked for.

  • Request → response → done. HTTP has no “subscribe”. The server can't start a conversation.
  • The response is a snapshot. It starts going stale the moment it arrives.
  • Nothing reaches the page unless the page asks again. Watch the server change on the right.
If an order ships 200 ms after your GET /orders, who tells the UI? Nobody — unless we add a mechanism. That mechanism is the rest of this section.
⏱ 6:20 — 40 seconds. Let the animation run: one request, one response, then the server's version keeps climbing while the browser sits on v1 marked "stale". Don't bash REST. REST is great at "give me the world as of now". It's silent about "tell me when the world moves". Transition: the obvious fix — ask again. And again.
PollingAsk on a timer

Polling: “are we there yet?”

The browser asks the same question on a timer. The server answers with whatever it has — usually nothing new.

  1. Every N seconds, send GET /orders.
  2. If something changed, re-render. If not, the request was wasted.
  3. A change waits for the next tick: worst-case latency = the interval.
Analogy

A kid in the back seat asking “are we there yet?” every five minutes. Simple, a bit annoying, and the answer is usually no.

⏱ 7:00 — 75 seconds. Let the simulation run and read the stats as they climb. Point at "Empty responses" — usually 60–80%. Point at "Avg delay" — about half the interval. Watch for the moment the server bubble says there's news and the browser is marked stale until the next tick. Narrate that gap: "the data exists, the user can't see it." Polling isn't shameful. It's the honest first solution because it uses the model we already have.
PollingDoing it well

Polling is often the right answer.

poll.js 

let etag;

async function poll() {
  const res = await fetch('/api/orders', {
    headers: etag ? { 'If-None-Match': etag } : {},
  });

  if (res.status === 200) {
    etag = res.headers.get('ETag');
    render(await res.json());
  } // 304 → nothing changed, almost free

  // setTimeout, not setInterval: requests never pile up
  setTimeout(poll, document.hidden ? 30_000 : 5_000);
}

poll();
The math: 1,000 open tabs polling every 5 s is 12,000 requests a minute — even when nothing happened.

Why it's great

  • Works through every proxy, CDN and auth setup you have
  • Stateless servers, trivial to scale and cache
  • Survives flaky networks by design

What it costs

  • Latency is the interval; average is half of it
  • Load tracks clients × time, not real events
  • Battery and data on mobile
Good fit

Admin pages, reports, “last updated 30 s ago” dashboards, anything where a human isn't staring at a spinner.

Three habits

setTimeout chains · back off when document.hidden · ETag / 304 so “no change” costs almost nothing.

⏱ 8:15 — 60 seconds. Walk the three habits in the code: ETag makes "no change" cheap, setTimeout avoids overlapping requests on slow networks, and hidden tabs back off to 30s. Ask the room: "What is an acceptable staleness window for your product?" That one number often kills a WebSocket proposal — or justifies it. React Query's refetchInterval and refetchOnWindowFocus are polling. Most of us already use it, and it's fine. Transition: can we keep HTTP but stop asking when there's nothing to say?
Long pollingAsk, then wait

Long polling: wait until there's news.

The browser asks once. The server holds the request open until there's news — or a timeout. Then the browser immediately asks again.

What it fixed

Near-instant delivery. No more empty answers every 5 s.

What still hurts

A full HTTP request per event: headers, cookies, auth.

The gap

Events between two requests need a cursor: ?since=42

Infrastructure

Proxies kill idle requests after 30–60 s.

Analogy

A waiter who stands at your table until the kitchen is ready.

⏱ 9:15 — 75 seconds. In the simulation, watch the request "park" at the server with a pulsing ring. When the server has news it answers instantly — delay drops to travel time. When the timeout hits, an empty response goes back and the browser re-asks. The gap card is the subtle one: after a response and before the next request arrives, the client isn't listening. You need a cursor (version/timestamp) so the server can say "here's what you missed". This is how Comet-era chat worked, and it's still the fallback transport in Socket.IO. Transition: what if the connection didn't have to end after every event?
Server-Sent EventsThe underrated one

Server-Sent Events: the server keeps talking.

One HTTP request. The response never ends. The server writes events into it whenever it wants.

  • Plain HTTP. Your cookies, proxies, load balancers and HTTP/2 just work.
  • One direction: server → client. Client writes stay normal fetch() calls.
  • The browser reconnects for you and tells the server the last event it saw, so nothing is lost.
Analogy

A radio station. You tune in once, then just listen. If the signal drops, the radio finds the station again.

⏱ 10:30 — 75 seconds. This is the most underused tool in the room. Let the simulation reach the connection drop: the line breaks red, the browser waits for "retry", reconnects with Last-Event-ID, and the server replays what was missed. You didn't write any of that reconnection code — EventSource did. Constraint on purpose: the client can't send on this connection. For "send a chat message" you POST. That's often a feature — you keep REST for writes, with all its validation and auth. Transition: let's look at what's actually on the wire — it's embarrassingly simple.

source.addEventListener('order-updated', (e) => {

⏱ 11:45 — 60 seconds. Point at the blank line between events — that's the whole framing format. You can literally curl this endpoint and read it. The id → Last-Event-ID loop is the killer feature. Server-Sent EventsWhen to reach for it

Server → client only? Reach for SSE first.

Where SSE shines
  • Notifications & feeds — badges, toasts, “someone commented”.
  • Dashboards — the server decides when numbers change.
  • Progress — uploads, exports, CI builds, long jobs.
  • Log tailing — append-only, ordered, resumable by id.
Gotchas worth knowing
  • EventSource can't set headers — use cookies, or fetch() + a reader.
  • Text only. Binary needs base64 — or a WebSocket.
  • ~6 connections per domain on HTTP/1.1, shared by tabs. HTTP/2 fixes it.
  • Proxies may buffer. Send X-Accel-Buffering: no.
chat.js — reading an AI response as it streams 

const res = await fetch('/api/chat', { method: 'POST', body });
const reader = res.body.pipeThrough(new TextDecoderStream()).getReader();

for (;;) {
  const { value, done } = await reader.read();
  if (done) break;
  appendTokens(value);   // "data: {…}\n\n" chunks, as generated
}
The one you use every day

ChatGPT-style token streaming is SSE framing over a POST. EventSource only does GET, so AI UIs read the same format with fetch and a stream reader.

⏱ 12:45 — 45 seconds. Ask: "How many of our 'we need WebSockets' tickets were actually SSE?" Let it hang for a second. AI streaming: OpenAI-style APIs stream with SSE framing over a POST. The browser's EventSource only does GET, so AI UIs usually use fetch + ReadableStream to read the same format. Same idea, different reader. The six-connection limit is the classic bug: seven tabs open on HTTP/1.1 and the seventh hangs. HTTP/2 fixes it. Transition: now — what if both sides need to talk?
WebSocketFull duplex

WebSockets: a phone call, not letters.

Starts as an HTTP request, then upgrades into a persistent connection where either side can send a message at any moment.

  • One TCP connection, both directions. Framing overhead is 2–14 bytes per message instead of a full set of HTTP headers.
  • No request/response. There are no status codes per message — you design the protocol: types, acks, versions.
  • Text or binary frames, with ping/pong control frames built in.
Analogy

A phone call. Once it connects, anyone can talk at any time — but someone has to notice when the line goes dead.

⏱ 13:30 — 75 seconds. Slow down: this is the deepest topic in the section. The simulation starts with the Upgrade handshake, then the wire "opens" and messages flow both ways. The small grey packets are heartbeats. Key idea: WebSocket is a transport, not a protocol. Once it's open you're on your own — message types, correlation ids, acknowledgements, versioning. That's work people forget to estimate. Use it when the client streams to the server too: chat with typing, presence, games, collaborative editing, trading. Don't go into server scaling (sticky sessions, pub/sub between nodes). If asked: "that's a backend session".

Why start with HTTP?

Same port 443, same TLS, passes through existing infrastructure, and the browser sends your cookies — so auth can happen right here.

After the 101

No headers per message, no status codes, no caching, no retries. Just frames. Everything HTTP gave you for free is now your job.

Close codes to recognise

1000 normal · 1001 going away (tab closed, deploy) · 1006 abnormal — no close frame, the network simply died.

⏱ 14:45 — 60 seconds. The Upgrade handshake is why WebSockets work almost everywhere: it looks like normal HTTPS until the 101. 1006 is the one you'll see in production logs: laptop lid closed, train tunnel, proxy killed an idle connection. You never get a clean close, which is why heartbeats matter (next slide). Transition: the browser API itself is tiny. Production is everything around it.

0 · CONNECTING1 · OPEN2 · CLOSING3 · CLOSED
Reconnection

It will drop. Exponential backoff plus jitter, so a deploy doesn't cause every client to reconnect in the same second.

Resync

After reconnecting you missed events. Refetch a snapshot or send your last-seen id. Never assume continuity.

Authentication

Cookie on the handshake, or a short-lived ticket. Tokens expire while the socket stays open — plan for re-auth.

Heartbeats

Ping/pong every 15–30 s. Half-open connections look alive until you try to use them.

Cleanup

Close on unmount. React Strict Mode mounts twice in dev. One socket per app, not per component.

Failure UX

Show “reconnecting…”, disable actions that need the socket, fall back to polling if it must always work.

⏱ 15:45 — 90 seconds. This is why the seniors are in the room — linger here. onclose fires for a clean shutdown and for a closed laptop lid. onerror is nearly useless for recovery; you recover from onclose. Real incidents worth a sentence each: reconnect without resync = ghost presence and duplicate toasts; every client reconnecting at the same second after a deploy = self-inflicted DDoS (that's what jitter prevents); "N sockets = tabs × components". ⏱ 20:00 — 20 seconds. Everything in chapter 1: we opened the connections, wrote the reconnect logic, and decided what to push and when. Seniors will be thinking "vendor lock-in" — acknowledge it, we'll get to the trade-offs. The lesson here is the layer, not the logo.
Real-time dataThe abstraction

Stop owning the pipe. Subscribe to the data.

Databases already record every committed change in a log — Postgres calls it the write-ahead log. A realtime service can read that log, filter it, and fan it out to subscribed clients.

This is change data capture. Your backend doesn't call broadcast(). It just writes to the database — and every write becomes an event.

Underneath it's still WebSockets, heartbeats and reconnection. You're buying them, not deleting them.

React UI
You write this: render from a cache that gets patched by events.
Subscription
You write this: channel.on('postgres_changes', …)
WebSocket
Connection, heartbeats, reconnect, re-join channels
Realtime service
Reads changes, applies filters and access rules, fans out
Change log
WAL / logical replication — every INSERT, UPDATE, DELETE
Database
The source of truth. Your backend just writes here.
Green = your code · grey = the platform
⏱ 20:30 — 90 seconds. Walk the layers bottom-up: the database commits a change; the change log records it; the realtime service reads the log and filters it; a WebSocket carries it; your subscription receives it; your UI patches its cache. The key insight: the interesting event is usually "a row changed", not "our Node process decided to emit". If the database is the source of truth, listen to the database. You still own two layers — the green ones. And they're where bugs live (coming up).
Real-time dataWhy it matters

Who is responsible for telling the UI?

The app pushes

  • Forget once and the UI silently lies until someone refreshes.
The database pushes

// that's it — the change feed does the rest
  • Every committed write is an event, no matter who made it — even a manual SQL fix.
  • The backend stays boring. Realtime becomes a property of the data, not of the code path.
You'll see both in the live demo. Same dashboard, two modes — and the event log will tell you who sent each update: app pushed or change feed.

Real-time dataThe frontend's job

The SDK owns the pipe. You still own correctness.

useLiveOrders.js 

useEffect(() => {
  const channel = supabase
    .channel('orders')
    .on('postgres_changes',
      { event: '*', schema: 'public', table: 'orders' },
      ({ eventType, new: row, old }) =>
        queryClient.setQueryData(['orders'], (list = []) =>
          eventType === 'DELETE'
            ? list.filter((o) => o.id !== old.id)
            : upsert(list, row)
        )
    )
    .subscribe((status) => {
      // first join AND every reconnect: resync the snapshot
      if (status === 'SUBSCRIBED') {
        queryClient.invalidateQueries({ queryKey: ['orders'] });
      }
    });

  return () => { supabase.removeChannel(channel); };
}, []);
  1. Subscribe narrowly. Filter by table, event and row. Too wide and you drown; too narrow and the UI lies.
  2. Patch the cache, don't replace the UI. The event is a delta; React Query or your store is the truth the UI reads.
  3. Resync on every (re)subscribe. Events that happened while you were offline are gone. Refetch the snapshot.
  4. Unsubscribe on unmount. Leaked channels are leaked memory, leaked money, and sometimes leaked data.
  5. Order and duplicates are your problem. Compare versions or timestamps before applying an event.
⏱ 26:30 — 2 minutes. This is the most practical slide in the chapter. The race: if you fetch first and subscribe second, any change in between is lost. If you subscribe first and fetch second, you can get an event older than your snapshot. The pattern here — invalidate on SUBSCRIBED — covers the first join and every reconnect. Optimistic updates plus realtime is a classic race: your optimistic write, then the server echo, then an older event. Decide on a rule (version wins). Ask: "Where does your source of truth live after an event arrives — the payload, or a refetch?"
Real-time dataTrade-offs

What you gain, and what you give up.

You gain

  • No connection infrastructure — no socket servers, sticky sessions or heartbeat code.
  • Every write is an event, from every code path, automatically.
  • Access rules at the data layer — the same policies protect queries and subscriptions.
  • Speed — a live feature in an afternoon instead of a sprint.

You give up

  • Your schema becomes the API. The UI couples to tables and columns.
  • Row events, not business events. “Status changed” isn't “order shipped, notify the customer”.
  • Event storms — a bulk update of 50,000 rows is 50,000 events.
  • Lock-in and less control over batching, payload shape and delivery guarantees.

Rule of thumb: realtime DBs are great at “keep this list in sync” — business reactions belong in your backend.

⏱ 28:30 — 90 seconds. This is where seniors earn their title: every row on the right is a production story. Event storms: a migration that updates every order will light up every connected client. Pause realtime or filter during bulk operations. Row events vs business events: great for "keep this list in sync", weaker for "do something meaningful when X happens". Business events belong in your backend — which is where webhooks come in.

WebhooksDelivery is at-least-once

The same event will arrive twice.

Webhook providers guarantee at-least-once delivery, not exactly-once. Design for it from day one.

  • Your endpoint was down or slow → they retry with backoff. Stripe keeps trying for up to three days.
  • Your 200 got lost on the way back → they think it failed and send it again.
  • Events can arrive out of order. “Updated” can land before “created”.
Watch the simulation: a failed delivery, a retry, and then a duplicate — processed exactly once because we remember event ids.
⏱ 35:30 — 2 minutes. Let the simulation run a full cycle. Narrate: first attempt hits a 500 (deploy in progress), Stripe backs off and retries, gets a 200 — then a duplicate arrives and is ignored because we've seen the event id. Frontend implication: duplicates flow downstream. UI handlers must be idempotent too — set status to paid, don't increment a counter per event, don't show a toast per event. Ask: "What happens in your system if the same payment event is processed twice?" If the answer is "we ship two pizzas", that's a bug waiting.
WebhooksThe rules

Five rules for every webhook endpoint.

webhooks.js 

app.post('/webhooks/stripe',
  express.raw({ type: 'application/json' }), // raw bytes!
  async (req, res) => {
    let event;
    try {
      event = stripe.webhooks.constructEvent(
        req.body, req.headers['stripe-signature'], secret
      );
    } catch {
      return res.sendStatus(400);        // 1. verify
    }

    if (await alreadyProcessed(event.id)) {
      return res.sendStatus(200);        // 2. idempotent
    }

    await queue.add(event);              // 3. work async
    res.sendStatus(200);                 // 4. ack fast
  });
  1. Verify the signature on the raw body before trusting a single byte.
  2. Be idempotent. Store processed event ids — a unique constraint is enough.
  3. Do the work asynchronously. Emails, fulfilment and third-party calls go to a queue.
  4. Acknowledge fast. A 2xx means “I've safely stored this”, not “I've finished”. Slow responses trigger retries.
  5. Don't trust order. Compare timestamps or re-fetch the object if you need the current state.
⏱ 37:30 — 90 seconds. Two stories if there's time: (1) processing inside the request, timing out, Stripe retries, you fulfil twice. (2) no idempotency: double emails, double stock decrements. Rule 5 is subtle: if you get "payment_intent.succeeded" then a late "payment_intent.processing", don't downgrade the order. Or re-fetch the PaymentIntent and trust its current status. Don't live-code HMAC. If asked: HMAC-SHA256 of "timestamp.rawBody", constant-time comparison, reject old timestamps.

Before you start

Do I actually need real-time?

“Live” in a product spec is not a reason to hold open a connection per tab. If a refresh or a 30-second poll is honest enough — ship that.

What real-time costs you

Reconnection · re-authentication · ordering · duplicates · resync · fan-out · stateful servers · a UI that must survive being wrong for a second.

Good defaults that aren't “real-time”

Refetch on window focus · invalidate after mutations · poll only while a screen is visible · a “new items” banner instead of live-shifting lists.

Where it earns its cost

A human is staring at the screen, waiting: checkout, chat, delivery, collaboration.

AppendixFor after the talk

A production-ish WebSocket hook.

useSocket.js 

export function useSocket(url, onMessage, resync) {
  useEffect(() => {
    let socket, timer, retry = 0, closed = false;

    const connect = () => {
      socket = new WebSocket(url);
      socket.onopen = () => { retry = 0; resync(); };
      socket.onmessage = (e) => onMessage(JSON.parse(e.data));
      socket.onclose = () => {
        if (closed) return;
        const base = Math.min(30_000, 1000 * 2 ** retry++);
        timer = setTimeout(connect, base * (0.5 + Math.random()));
      };
    };

    connect();
    return () => {
      closed = true;
      clearTimeout(timer);
      socket.close(1000);
    };
  }, [url]);
}
  1. Exponential backoff capped at 30 s — don't hammer a server that's already struggling.
  2. Jitter (0.5 + random) spreads reconnects after a deploy so they don't arrive in the same second.
  3. Resync on open — refetch the snapshot or send your last-seen id.
  4. The closed flag prevents reconnecting after unmount (and Strict Mode's double mount).
  5. Not shown: heartbeats, auth refresh, a message queue while disconnected. That's why libraries exist.
